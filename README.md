# DeepSeek Harness

English | [中文](README.zh.md)

DeepSeek Harness (`dsh`) is an open-source agent harness developed by [DeepSeek AI](https://deepseek.com).

It is built on an **everything-is-a-plugin** architecture and powered by [Cordis](https://github.com/cordiverse/cordis), whose design is described in [_A Programming Paradigm for Spatiotemporal Composability_](https://arxiv.org/abs/2608.25512).

Documentation: [https://deepseek-harness.github.io/deepseek-harness/](https://deepseek-harness.github.io/deepseek-harness/)

## Developer preview

DeepSeek Harness is in _developer preview_ and iterating rapidly. **THERE WILL BE COMPATIBILITY-BREAKING CHANGES.**

Review the [safety notice](SAFETY.md) before running the project.

## Linux build (unofficial)

> **Unofficial build.** This branch is a personal fork. It is **not affiliated with, sponsored by, or endorsed by DeepSeek**. There is no official Linux Desktop support, no support commitment, and no guarantee that these artifacts are safe for production or will be maintained. Upstream's packaging guide still says "Linux is not a supported Desktop release target."

This branch adds a local, unsigned `linux-x64` Desktop build. It produces an RPM and an AppImage from the same packaging pipeline as the macOS/Windows builds, with a Linux-specific workaround for sharp described below.

### Tested setup

| Item | Value |
|---|---|
| Distribution | Fedora Linux 44 (KDE Plasma Desktop Edition) |
| Desktop | KDE Plasma 6.7.5 / KWin 6.7.5 |
| Session | Wayland (`XDG_SESSION_TYPE=wayland`) |
| Architecture | x86_64 |
| Kernel | `7.2.11-200.fc44.x86_64` |
| Node used for packaging | 24.22.0 (packaging run record) |
| pnpm used for packaging | 11.28.5 (repository pin; local logs report 11.28.5) |

Only this setup was tested. X11, other distributions, ARM64, and other GPU vendors are untested.

### Prerequisites

#### Runtime

- **Fedora 44 x86_64** (the tested target). Other glibc distributions may work but are untested.
- **`libxcrypt-compat`**:

  ```sh
  sudo dnf install libxcrypt-compat
  ```

  Fedora 44 does not install `libcrypt.so.1` by default (`libxcrypt-compat` is a separate package). The bundled Python's `_crypt` extension links against it, so `import crypt` fails without the compatibility package. On the tested machine the Desktop GUI itself started without the system package installed, so this is primarily a bundled-Python requirement; install it to match the tested environment.

- **~1.1 GB free disk** for the installed RPM payload (the installed size reported by RPM is 1,096,554,466 bytes). The build tree and AppImage need considerably more.

#### Build

- **git**
- **Node.js** matching the repository's `engines` field (`^22.19.0 || >=24.0.0`); the tested build used Node 24.22.0.
- **pnpm 11.28.5**, which is the version pinned by the root `package.json` (`"packageManager": "pnpm@11.28.5"`). Do not assume a newer global pnpm is equivalent; the repository pins 11.28.5 and the local environment reported 11.28.5 during the build. With Corepack:

  ```sh
  corepack enable
  corepack prepare pnpm@11.28.5 --activate
  ```

  If you prefer a standalone install, install that exact version and check `pnpm -v` before building.

- **`rpm-build`** (provides `rpmbuild`) for the RPM target:

  ```sh
  sudo dnf install rpm-build
  ```

- A network connection for the first build: the pipeline downloads Electron and the pinned runtime payloads.

### Build

```sh
git clone https://github.com/dahch/deepseek-harness.git
cd deepseek-harness
git checkout linux-desktop

corepack enable
corepack prepare pnpm@11.28.5 --activate
pnpm install --frozen-lockfile

pnpm run package:desktop:linux:x64
```

The build writes to:

```
apps/desktop/.desktop-build/targets/linux-x64/unsigned-artifacts/
├── deepseek-harness-0.2.1-rc.2-linux-x86_64-unsigned.AppImage
├── deepseek-harness-0.2.1-rc.2-linux-x86_64-unsigned.rpm
└── linux-unpacked/
```

The build is long and downloads dependencies on first use. If it fails, the packaging run records stage logs under `apps/desktop/.desktop-build/packaging-runs/`.

### Install

#### RPM

```sh
sudo dnf install ./apps/desktop/.desktop-build/targets/linux-x64/unsigned-artifacts/deepseek-harness-0.2.1-rc.2-linux-x86_64-unsigned.rpm
```

Launch it from the application menu or run:

```sh
"/opt/DeepSeek Harness/deepseek-harness"
```

Remove it with:

```sh
sudo dnf remove deepseek-harness
```

#### AppImage

```sh
chmod +x ./apps/desktop/.desktop-build/targets/linux-x64/unsigned-artifacts/deepseek-harness-0.2.1-rc.2-linux-x86_64-unsigned.AppImage
./apps/desktop/.desktop-build/targets/linux-x64/unsigned-artifacts/deepseek-harness-0.2.1-rc.2-linux-x86_64-unsigned.AppImage
```

The AppImage desktop entry generated by electron-builder uses `AppRun --no-sandbox %U`. If your system cannot run AppImages directly (for example, no FUSE), use your distribution's extract-and-run mechanism; that path was not tested here.

### What was tested

- The unpacked Linux application launched on the setup above and opened the `dsh-app://` window.
- The Desktop Host process ran under the bundled standalone Node (`resources/runtime/primary-runtime/dependencies/node/bin/node`), not Electron Node mode.
- The renderer used Wayland (`--ozone-platform=wayland`).
- A second launch exited with code 0 immediately.
- Closing the main window exited the launched application process.
- The AppImage was extracted and its payload inspected (not launched).
- The RPM was inspected (not installed).
- sharp worked under the bundled Node and crashed under Electron Node mode; the branch's workaround is described below.

Not tested in this pass: installing the RPM, launching the AppImage, X11, other distributions, ARM64, signing, auto-update, or the complete packaging pipeline from a clean clone.

### Why the Host does not use Electron's Node on Linux

Electron's Linux Node mode leaks system glib symbols into libvips, and sharp's image decode segfaults (exit 139) when the Host processes an image attachment. sharp documents this as a known Electron/Linux conflict and points to [electron#46323](https://github.com/electron/electron/issues/46323). A small sharp decode crashes under `ELECTRON_RUN_AS_NODE=1` and succeeds under the bundled standalone Node.

The workaround keeps Electron for the shell and runs the Host under the bundled Node. Standalone Node cannot read ASAR, so the prepared dsh tree is shipped as real files at `resources/dsh` (about 418 MB) instead of inside `app.asar`. The packaged-runtime smoke runs under the same interpreter. macOS and Windows still use Electron Node mode.

This is a workaround, not a fix for the underlying Electron/sharp conflict. It also means the Linux payload is larger and not ASAR-protected, and any code that assumes `resources/app.asar/dsh` needs updating.

### Known limitations

- **Unsigned.** The RPM has `Signature: (none)`; the AppImage is unsigned. There is no GPG signature or code signing. Verify the SHA-256 above.
- **Release candidate.** The build is `0.2.1-rc.2`, not a stable release.
- **No auto-update.** The unsigned Linux target resolves no update feed (`publish` is `null`); the upload, retention, and release-record paths reject `linux-x64`. Linux updating and publishing are out of scope for this branch. Do not expect the update menu to work.
- **Not official.** Upstream does not support Linux Desktop. The branch changes no upstream documentation or CI; upstream's docs still describe `resources/app.asar/dsh` and the macOS/Windows process.
- **One tested configuration.** Fedora 44 KDE Plasma 6.7.5 on Wayland/x86_64 only. X11, GNOME, other distributions, ARM64, and GPU-specific issues are untested.
- **GPU process crashes were observed.** On the tested machine the log showed repeated `GPU process exited unexpectedly: exit_code=139` and `drmGetDevices2() has not found any devices`, while the window still opened and the page loaded. The cause was not investigated; do not treat the GPU path as validated.
- **The Linux CLI launcher is stale.** `apps/desktop/cli/dsh-linux` still points at `resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-desktop-host/lib/cli.js`, but this branch moved the tree to `resources/dsh`. `app.asar` contains no `dsh` directory. The launcher also uses `ELECTRON_RUN_AS_NODE=1`, the mode that crashes sharp. Do not rely on the bundled `dsh-linux` launcher until it is fixed and tested.
- **The AppImage's generated desktop entry uses `--no-sandbox`.** It launches `AppRun --no-sandbox %U`; this was not changed or security-reviewed.
- **Bundled Python `crypt` needs `libxcrypt-compat`.** See the prerequisite above.
- **Product analytics is enabled by default.** See the next subsection.

### Product analytics

**The Linux build sends Desktop product analytics by default.** I verified this with a local OTLP collector, not by inspecting logs alone.

- The Desktop composition mounts `@deepseek-ai/dsh-host-product-telemetry-otel` and `@deepseek-ai/dsh-client-product-analytics` with `enabled: true`, gated on the `desktop` profile. The Linux build uses that profile.
- The collector endpoint defaults to `https://dsh-otel-collector.deepseeksvc.com/v1/logs`; the service name is `deepseek-harness-desktop`.
- With `DSH_PRODUCT_ANALYTICS_OTLP_URL` pointed at a local sink, the packaged Linux build POSTed `desktop_app_launch` and `auth_page_view`. The payload included `os_name=linux`, `os_version=linux 7.2.11-200.fc44.x86_64`, `app_arch=x64`, CPU model and logical count, total memory, and `app_version=0.2.1-rc.2`. Identity fields are included when an account is signed in; that run was not signed in.
- The Linux port does not add Linux-specific metadata: `os_arch`, `os_build`, `os_version_full`, and `cpu_physical_core_count` were reported as `unsupported` in `missing_fields`.
- There is **no user-facing analytics toggle** in this build. `DSH_PRODUCT_ANALYTICS_OTLP_URL` redirects the export destination; it is not a disable switch. I did not find or verify a supported way to turn collection off. If that is unacceptable, do not run this build, or block `dsh-otel-collector.deepseeksvc.com` at the network level (not tested here).
- I verified delivery to a local sink, not to the production collector.

This is inherited Desktop behaviour, not something this Linux branch adds. It is called out here because an unofficial Linux build should not silently send telemetry.

## Run

### Run from `npm`

Install `Node.js`, then run:

```sh
npx @deepseek-ai/dsh web
```

The command starts the Web UI at `http://127.0.0.1:3080` by default and opens it in the default browser for a local launch. An SSH launch only prints the host URL because the SSH client or editor owns the local forwarded address. Pass `--no-open` to run the server without opening a browser. See [Web UI guide](docs/user/guide/index.md).

### Run from source

To run from a repository checkout:

```sh
git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
pnpm install
pnpm run build
pnpm dsh web
```

`pnpm run build` prepares the repository artifacts. `pnpm dsh web` uses those built artifacts without rebuilding.
